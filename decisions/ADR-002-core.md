# ADR 002 Ядро и хранение

Статус: принято как рабочая архитектура реализации, 15.11.2026.

Рассмотрены три альтернативы: отдельные таблицы и CRUD для каждого типа; единая таблица материалов с JSON-полями по конфигурации; универсальная EAV-модель с записью каждого значения отдельной строкой. Критерии: добавление типа без правки ядра, доступность SQL-запросов для аналитики, простота валидации, объём кода.

Выбрана единая таблица со стабильными общими колонками и JSON дополнительных полей. Типы задаются JSON-схемами, версия схемы фиксируется миграцией реестра. Для SQLite не нужны отдельный сервис и драйвер. Связи таксономии и ревизии хранятся отдельно. Цена решения: для поиска по произвольным дополнительным полям нужны отдельные индексы или развитие запросов.

Отвергнуто предложение трактовать новый тип как новую Python-модель: оно нарушает проверяемое требование добавления конфигурацией. EAV не выбран из-за сложности ограничений типов и избыточных соединений для небольшого портала. Решение сформулировано до генерации ядра в SPEC 00 и 01.
