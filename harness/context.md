# Управление контекстом

В начале задачи: SPEC, соответствующий ADR, контракт API и только затрагиваемые файлы и тесты. Корень для изменений — cms/. Учебные данные из data/ не читаются без необходимости; .env не попадает в контекст.

При разделении задачи агент ядра получает core.py, schemas/, migrations/ и test_core.py; агент интерфейсов получает app.py, templates/, static/ и test_web.py. Общий контракт передаётся явно до реализации. Это предотвращает конкурентную перезапись файлов.

При переполнении контекста сохранить краткую сводку: цель SPEC, выполненные изменения, текущий результат тестов, нерешённый дефект и следующий шаг. Новый запуск начинает с этой сводки и точечных чтений, а не с загрузки всех журналов и зависимостей.

Реальный пример разделения контекста и ролей: трассы core-session.jsonl и web-session.jsonl. В них сохранены постановки и обмен контрактом; ответственность за сведение результатов остаётся у основного агента и последующую приёмку у студента.
